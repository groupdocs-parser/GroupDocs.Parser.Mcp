# 26.10.2 — explain a write the container cannot make, document `--user` for Docker on Linux

## What changed

- **Permission failures now carry the fix.** When a tool fails because the process may not write —
  an `UnauthorizedAccessException` anywhere in the chain, or the OS "Permission denied" /
  "Read-only file system" — the error text gains a trailing hint: *"Fix: the server cannot write to the
  output folder. In Docker on Linux the container runs as a non-root user, so a host folder you own is
  read-only to it: add --user "$(id -u):$(id -g)" to docker run (in a JSON client config use the numbers,
  e.g. "--user", "1000:1000"), or point GROUPDOCS_MCP_OUTPUT_PATH at a writable mounted folder."*
  The prefix (`Image extraction failed for '<file>': …`) is unchanged, so existing matching keeps working.
- **Unlicensed JSON responses parse again.** `extract_barcodes` and `extract_tables` (`format: "json"`)
  prefixed unlicensed output with `[Evaluation mode] Output may be limited.` Callers find the JSON array
  by its first `[` — the documented `extract_barcodes` shape is a header line followed by the array — so
  the note's own bracket was taken as the array start and parsing failed
  (`'E' is an invalid start of a value`). The note now reads `Evaluation mode: output may be limited.`
  in these two tools. `extract_text` and `extract_images` return no JSON and keep their wording.
- **Releases started from the Actions tab now build the image.** `Publish Prod` run by hand creates the tag
  with the workflow token, and GitHub does not let that tag trigger `publish_docker.yml` — so the registry job
  waited for an image that was never built and failed with "image not on GHCR yet (HTTP 403)". The registry
  job now starts `publish_docker.yml` on the release tag when the run was manual (skipped when the image already
  exists or a build is in progress), and waits up to 15 minutes instead of 10. Tag pushes are unchanged.
- **README:** new section *Linux: run the container as your user*, with the numeric form for JSON configs.
- Unit tests for the hint (`ToolErrorTests`); `InternalsVisibleTo` for the unit-test project.

**26.10.0 was released on GitHub but never published.** `Publish Prod` was started by hand on 2026-10-07: it
created the `26.10.0` release and tag, but no Docker build ran, so GHCR has no `26.10.0` image and the MCP
Registry job timed out (the registry still lists 26.9.0). This release is the first to ship its changes as well: GroupDocs.Parser 26.8.0, metered licensing declared in `server.json`
and documented, the empty-text fix for documents without a text layer, and the `.dockerignore`
(see `005-26.10.0-engine-26.8-and-metered-parity.md`).

## Why

The integration suite's docker job has failed on `ubuntu-latest` since it was added:
`extract_images` on `images.pdf` and `images.xlsx` returned
`Access to the path '/data/images_image1.jpeg' is denied. | inner(0): System.IO.IOException: Permission denied`.
The image runs as uid 1654; on a Linux host a bind mount keeps its host owner, so the runner's folder —
and any folder a Linux user owns — is read-only inside the container. The same cause broke the first
GroupDocs.Search.Mcp CI run, which is where it was diagnosed. Docker Desktop on Windows and macOS does
not enforce bind-mount ownership, so the problem never showed locally.

The same CI run had two more failures — `ExtractBarcodes_BarcodesPdf_FindsAtLeastOneBarcode` and
`ExtractTables_InvoicePdf_JsonFormatReturnsValidJson` — both the bracket problem above, visible only in
evaluation mode, which is how CI runs.

## Migration impact

Unlicensed `extract_barcodes` / `extract_tables` JSON responses start with `Evaluation mode:` instead of
`[Evaluation mode]`; a caller matching the old bracketed text should match `Evaluation mode` instead.
Otherwise none. Linux Docker users who use `extract_images` add `--user "$(id -u):$(id -g)"` (or the
numeric form in JSON configs). The read-only tools are unaffected.
